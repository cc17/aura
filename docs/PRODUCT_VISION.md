## 2. 产品由三块能力构成

```
┌─────────────────────────────────┐
│  Buddy 能力(粘性层)            │
│  - 用户画像(动态)              │
│  - 长期记忆                     │
│  - 个性化推荐                   │
├─────────────────────────────────┤
│  行业解决方案(价值层)          │
│  - 行业知识库                   │
│  - 场景化工作流(Skills)        │
│  - 现成模板和工具调用            │
├─────────────────────────────────┤
│  基础对话能力(底座,已存在)    │
│  - LLM 调用                     │
│  - 对话历史                     │
│  - 前端 UI                      │
└─────────────────────────────────┘
```

**关键认知**:
- 三块能力**不是分离的**,是互相增强的
- 用户付费是为"行业解决方案",留存是因为"Buddy 能力",对话是基础
- 任何改造都应同时考虑这三层的协同

## 3. 当前阶段目标

**阶段定位**:内部 MVP,用研发助理团队当测试田跑通流程。

**不是要做的**:
- ❌ 不是要做面向 C 端公开发布的产品
- ❌ 不是要追求大而全的功能覆盖
- ❌ 不是要做付费转化优化

**是要做的**:
- ✅ 验证 Buddy 能力(画像 + 记忆 + 推荐)能否工程化跑通
- ✅ 验证"行业 Skills"这一抽象在研发助理场景下能否成立
- ✅ 验证整套架构的可扩展性(将来要平移到其他行业)

---

## 4. 首批目标用户:互联网研发助理

**画像**:
- 岗位:研发团队的助理/项目协调/流程跟进
- 技术背景:非开发,但熟悉互联网工作流
- 工作内容:文档处理、会议协调、需求整理、跨部门沟通、Bug 跟进

**典型痛点**:
1. 写需求评审会议纪要(耗时长,格式不统一)
2. 整理研发周报(数据散在 Jira / 飞书 / 文档)
3. 跟进 bug 状态(要一个个问)
4. 协调跨部门会议(排时间、发议程、催参会)
5. 整理需求池(各种渠道收来的需求,要分类)
6. 月度 OKR 复盘(数据散在各处)

**这些痛点是 Skills 设计的依据。**

## 5. 关键产品决策(已确定,不要质疑)

| 决策项 | 选择 | 原因 |
|---|---|---|
| 形态 | Web 应用(已有) | 迭代快,不用过审 |
| 后端 | Python/Node(已有) | 沿用现有 |
| 数据库 | PostgreSQL + pgvector | 一个库搞定结构化+向量 |
| 主模型 | DeepSeek-V3 或 Claude Sonnet | 中文好,成本可控 |
| 辅助模型 | DeepSeek-Lite / Qwen-Turbo | 用于画像更新、推荐生成等轻量任务 |
| 记忆方案 | 自研(可控) | 不依赖第三方框架 |

---

## 6. 不在本期范围

以下内容**本期不做**,Claude Code 不要主动实现:

- ❌ 多模态(语音、图片输入)
- ❌ 移动端 App
- ❌ 微信生态接入
- ❌ 付费订阅系统
- ❌ 多租户/企业版
- ❌ 主动 Push 通知(预留接口即可)
- ❌ 复杂的权限系统
